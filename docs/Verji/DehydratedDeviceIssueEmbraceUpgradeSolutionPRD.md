# PRD — Embrace-Upgrade Client Solution for Dehydrated Device Issue

> **Status:** Draft for review
> **Author:** Engineering
> **Date:** 2026-04-30
> **Related:** [DehydratedDeviceIssue.md](DehydratedDeviceIssue.md), [DehydratedDeviceIssueRollbackClientSolutionPRD.md](DehydratedDeviceIssueRollbackClientSolutionPRD.md)

## 1. Context

Per [DehydratedDeviceIssue.md](DehydratedDeviceIssue.md), dehydrated devices are broken on `element-web-v2`. Three independent layers contribute: Verji's `getDehydrationKey` callback wiring is dead on Rust crypto; the Rust SDK's MSC3814 dehydration uses a different key model than Verji's MSC2697 design; Verji's deployed Synapse only implements MSC2697. The sibling [Rollback PRD](DehydratedDeviceIssueRollbackClientSolutionPRD.md) evaluates *retreating* to the legacy 1.11.68 client to preserve dehydration. This PRD evaluates the *opposite* direction: pushing forward, fully adopting MSC3814 on the new Rust-only stack, and engineering an explicit migration that does not lose user messages.

The framing of this document is: **if Verji accepts that Rust crypto and MSC3814 are the future, what does it cost to actually get there, and how do we cut over without dropping a single in-flight or already-delivered to-device event?**

This PRD does not take a position on whether the embrace path or the rollback path is correct overall — it makes the embrace path concrete enough that leadership can compare it against the Rollback PRD on equal terms.

## 2. Problem statement

Verji needs a client that:

1. Implements MSC3814 dehydrated devices on the Rust crypto backend.
2. Continues to consume the SSO-supplied `secure_backup_key` as the 4S unlock key (so the existing zero-prompt SSO flow is preserved).
3. Creates a fresh dehydrated device on every active session and rehydrates an existing one on login, so room keys delivered while the user is offline are recoverable.
4. **Drains all pending to-device events from any pre-existing MSC2697 ghost device before that device is orphaned.** This is the part that earns this PRD: a naive cutover loses every offline-delivered key currently sitting on a legacy ghost.
5. Continues to receive upstream security patches and stays close to upstream Element.

`element-web-v2` already satisfies (5) and the SDK already implements (1) and (3). What is missing is wiring (1) into element-web-v2's lifecycle, reshaping the cryptosetup module to the new key model (2), and most critically engineering the migration drain (4).

## 3. Goals & non-goals

**Goals**

- Full MSC3814 support on `element-web-v2`: dehydrated device created on every session, rehydration on every login, periodic refresh.
- Zero message loss for in-flight or already-delivered keys on legacy MSC2697 ghost devices.
- Clean, observable, reversible cutover with telemetry.
- Deprecate Verji's MSC2697 client wiring once migration is complete.

**Non-goals**

- Backporting MSC2697 to the Rust SDK or maintaining a hard fork of matrix-js-sdk.
- Supporting both crypto stacks long-term in the same client build.
- Preserving the "SSO key == dehydration key" identity. Under MSC3814 these are different keys by design; the contract changes.
- Solving server-side MSC3814 implementation. This PRD assumes Synapse is being upgraded by another team (this is the same dependency the Rollback PRD identifies as the "unblock condition").

## 4. The contract change at a glance

The current Verji design (legacy stack):

| Key | Purpose | Source |
|---|---|---|
| `mx_secure_backup_key` (4S key) | Unlock 4S, also used as dehydration key | SSO login response |

The new design (Rust + MSC3814):

| Key | Purpose | Source |
|---|---|---|
| `mx_secure_backup_key` (4S key) | Unlock 4S only | SSO login response (unchanged) |
| Dehydration key | Encrypt/decrypt the dehydrated device | Random 32 bytes generated by the SDK, stored *inside* 4S under name `org.matrix.msc3814` ([DehydratedDeviceManager.ts:155-160](../../../matrix-js-sdk-v2/src/rust-crypto/DehydratedDeviceManager.ts#L155-L160)) |

The SSO key still does its job (unwrap 4S). Dehydration just stops being a special case: the SDK creates and rotates its own key, persisted via 4S, and we never have to think about it after bootstrap. The legacy `cryptoCallbacks.getDehydrationKey` callback is no longer consulted by anything ([client.ts:1778](../../../matrix-js-sdk-v2/src/client.ts#L1778) — the only caller is the deprecated MSC2697 `rehydrateDevice()`).

## 5. Solution architecture

Four workstreams. They must complete before user-facing rollout but can be developed in parallel.

### W1 — Synapse MSC3814 (server)

Out of scope for client engineering, but the gating dependency:

- Deploy a Synapse version that implements MSC3814 endpoints under `/_matrix/client/unstable/org.matrix.msc3814.v1` ([DehydratedDeviceManager.ts:47](../../../matrix-js-sdk-v2/src/rust-crypto/DehydratedDeviceManager.ts#L47)).
- Advertise `org.matrix.msc3814` in `.well-known`. Required by the gate at [dehydration.ts:32](../../src/utils/device/dehydration.ts#L32) — without the well-known flag, the client refuses to start dehydration even if the endpoints work.
- Validation: `GET /_matrix/client/unstable/org.matrix.msc3814.v1/dehydrated_device` returns 404 (not 401, not `M_UNRECOGNIZED`) when no device is stored.

A client-side fallback is possible (relax the well-known gate, trust `isSupported()` alone) — described in §11 as a contingency if server can't be persuaded to update the well-known file.

### W2 — Client wiring (element-web-v2)

The SDK already does the heavy lifting. What's missing in `element-web-v2` is the call site.

- Replace the dead [MatrixClientPeg.ts:348](../../src/MatrixClientPeg.ts#L348) `// TODO: device dehydration and whathaveyou` with a call to `initialiseDehydration()` ([utils/device/dehydration.ts:43-49](../../src/utils/device/dehydration.ts#L43-L49)). This must run after `initRustCrypto` succeeds **and** after 4S + cross-signing are confirmed ready, since [rust-crypto.ts:1402-1406](../../../matrix-js-sdk-v2/src/rust-crypto/rust-crypto.ts#L1402-L1406) throws otherwise.
- The two existing call sites — [SetupEncryptionStore.ts:153](../../src/stores/SetupEncryptionStore.ts#L153) and [CreateSecretStorageDialog.tsx:335](../../src/async-components/views/dialogs/security/CreateSecretStorageDialog.tsx#L335) — handle the *first-time setup* paths only. They do not cover normal login when 4S is already bootstrapped, which is the common case for a returning Verji user. The new call site closes that gap.
- Recommended placement: `MatrixClientPeg.assign()` (or a new `MatrixClientPeg.initDehydration()` invoked from the post-login Lifecycle path), guarded by `await crypto.isCrossSigningReady() && await crypto.isSecretStorageReady()`. Errors must be caught and logged but not fatal — dehydration is best-effort.
- Wrap the call in a UIFeature flag (suggested name `UIFeature.DehydratedDevices`) registered alongside the existing flags in [Settings.tsx](../../src/settings/Settings.tsx) and consumed via `SettingsStore.getValue(UIFeature.DehydratedDevices)`. This gives ops a runtime kill-switch during rollout. Document the flag in [VerjiConfig.md](VerjiConfig.md) per the standard 4-edit pattern from [CLAUDE.md](../../../CLAUDE.md).
- Cleanup deferred to W2.5: delete the dead `getDehydrationKey` wiring at [MatrixClientPeg.ts:448-457](../../src/MatrixClientPeg.ts#L448-L457), the `// VERJI - Dead code?` block at [SecurityManager.ts:162](../../src/SecurityManager.ts#L162), and the orphan `rust_crypto_*` translations in [src/i18n/strings/nb_NO.json](../../src/i18n/strings/nb_NO.json) lines 2038–2043. Cleanup happens *after* a quarter of stable production traffic on MSC3814, not during cutover.

### W3 — Cryptosetup module update (`verji-cryptosetup-module`)

The module's interface needs a new minor version. The `secure_backup_key` from the SSO response is still authoritative for 4S unlock; only the dehydration-specific surface changes.

- **Keep**: `examineLoginResponse()` and `persistCredentials()` ([VerjiCryptoSetupModule.tsx:21-34](../../../verji-cryptosetup-module/src/VerjiCryptoSetupModule.tsx#L21-L34)) — still needed; SSO key still becomes the 4S unlock key.
- **Keep**: `getSecretStorageKey()` ([VerjiCryptoSetupModule.tsx:36-42](../../../verji-cryptosetup-module/src/VerjiCryptoSetupModule.tsx#L36-L42)) — still consulted by 4S unwrap path.
- **Drop**: `getDehydrationKeyCallback()` ([VerjiCryptoSetupModule.tsx:86-95](../../../verji-cryptosetup-module/src/VerjiCryptoSetupModule.tsx#L86-L95)) — Rust never calls it. Removing it from the module also lets us delete the wiring at [MatrixClientPeg.ts:452-457](../../src/MatrixClientPeg.ts#L452-L457).
- **Verify**: Verji's SSO bootstrap must leave 4S in a state where `isSecretStorageReady()` returns true on the next login — i.e. `m.secret_storage.default_key` and the 4S algorithm entry are both set in account data, not just the in-memory key cache. If `accessSecretStorage()` ([SecurityManager.ts:283](../../src/SecurityManager.ts#L283)) is racing the dehydration init, the SDK gate trips and dehydration silently doesn't start.
- Module versioning: ship as `@verji/verji-cryptosetup-module` v2 (major bump because the module-api surface changes). The legacy element-web stack continues to consume v1 during the bridge.

### W4 — Migration drain ("no message loss")

The contract this PRD is asked to honor. See §6 — the dedicated section.

## 6. The drain — protecting in-flight and already-delivered keys

Pre-existing MSC2697 ghost devices on Verji's Synapse hold accumulated to-device messages (room keys) for users who have been offline. After the cutover those ghost devices are orphaned: wrong key, wrong endpoint, wrong spec — the new client cannot reach them ([DehydratedDeviceIssue.md §"Layer 2"](DehydratedDeviceIssue.md)). A naive cutover loses every key sitting on every legacy ghost. The user has stated this is unacceptable.

Three sub-strategies:

### Strategy A — Coordinated final rehydration on the legacy stack (recommended)

Every active user runs the legacy `element-web/` (1.11.68) client one final time before being upgraded to v2. The legacy client performs its standard MSC2697 rehydration on that final login, draining all pending to-device events from the existing ghost. v2 then takes over with MSC3814 and creates a fresh ghost.

Operationalised by:

- Patching the legacy `element-web/` to write a per-user account-data flag (e.g. `com.verji.dehydration_drain_complete`) immediately after `MatrixClient.rehydrateDevice()` succeeds.
- Adding a per-user feature gate in v2's bootstrap: if the flag is missing, the user is held back on legacy. If the flag is present, v2 enables MSC3814 and creates a new ghost.

**Pros**

- Zero in-flight loss for any user who logs into legacy at least once during the migration window.
- Deterministic: the drain success is recorded in account data and observable.
- Reuses the existing, working legacy rehydration path. No new server tooling.

**Cons**

- Requires shipping a small patch to legacy `element-web/` (the drain-flag write).
- Requires a per-user feature-flag mechanism in v2's load-time check. If Verji doesn't already have user-targeting infra at the client load stage, this needs to be built — but it is at most ~50 lines.
- Cannot drain users who never log into legacy during the window (covered by Strategy B).

### Strategy B — Server-side ghost device drain

A one-shot Synapse admin script enumerates legacy MSC2697 ghost devices that still have pending to-device events and forwards those events to the user's *new* MSC3814 ghost (which exists once the user has logged into v2 once). Acts as belt-and-braces for users who never returned to legacy during the Strategy A window.

**Pros**

- Catches the long-tail of users who skip the migration window entirely (e.g., on holiday).
- Operates once after rollout is complete, so it can run with full ground truth.

**Cons**

- Requires Synapse admin tooling that doesn't yet exist; coordination with the server team.
- Chicken-and-egg: the new MSC3814 ghost only exists after the user logs into v2 once. The script needs to operate on a per-user delay basis, not at a single instant.
- Potential edge cases: if the ghost's encrypted account blob format differs between legacy and the rehydrated state, blind forwarding may fail. Needs validation.

### Strategy C — Accept-and-minimize

Don't drain. Rely on the property that lost room keys mostly damage history viewing of *recently-rotated* rooms, not future messages. Use a slow staged rollout (5% → 25% → 100%) and watch UTD telemetry for spikes.

**Pros**: simplest. No new tooling.

**Cons**: violates the user's stated "zero message loss" constraint. **Rejected.**

### Recommendation

**Strategy A as primary, Strategy B as belt-and-braces, Strategy C explicitly rejected.**

This combination meets the no-loss constraint for active users and provides a recovery path for inactive ones, at the cost of a small legacy patch and a one-shot server script.

## 7. Rollout plan

Phased, with explicit exit criteria per phase.

### Phase 0 — Server readiness

- [ ] Synapse MSC3814 deployed to staging.
- [ ] `.well-known` updated with `org.matrix.msc3814: true`.
- [ ] `GET /dehydrated_device` returns non-`M_UNRECOGNIZED` for an authenticated request.
- [ ] Exit: client `crypto.isDehydrationSupported()` returns `true` against staging.

### Phase 1 — Client wiring

- [ ] W2 patches landed on `element-web-v2/verji-develop`. New call site invoking `initialiseDehydration()` post-login. 4S/cross-signing-readiness gate in place.
- [ ] `UIFeature.DehydratedDevices` flag registered ([UIFeature.ts](../../src/settings/UIFeature.ts), [Settings.tsx](../../src/settings/Settings.tsx)) and documented in [VerjiConfig.md](VerjiConfig.md) and [config.verji.samlple.json](../../config.verji.samlple.json). Flag default: `false`.
- [ ] W3 module v2 published to GitHub Packages.
- [ ] Internal staging build wired: flag flipped to `true` in `config.verji.json`. Verified end-to-end against staging Synapse.
- [ ] Exit: a test user logging in fresh on staging produces `dehydration: uploaded device` log line ([DehydratedDeviceManager.ts:277](../../../matrix-js-sdk-v2/src/rust-crypto/DehydratedDeviceManager.ts#L277)).

### Phase 2 — Legacy drain patch

- [ ] Patch shipped to legacy `element-web/` `verji-develop` that writes `com.verji.dehydration_drain_complete` account-data flag after a successful `rehydrateDevice()`.
- [ ] Build deployed to production legacy users.
- [ ] Exit: drain flag observed in account data for users who have logged in since the patch shipped.

### Phase 3 — Production Synapse cutover

- [ ] Synapse MSC3814 deployed to production.
- [ ] `.well-known` flipped on in production.
- [ ] Exit: `crypto.isDehydrationSupported()` returns `true` against production.

### Phase 4 — Per-user staged rollout to v2

- [ ] Cutover gate added to v2 bootstrap: a user is moved to v2 only if `com.verji.dehydration_drain_complete` is set.
- [ ] 5% rollout. Monitor: server-side count of newly-created MSC3814 ghosts; per-user UTD events; client logs for `dehydration: received N room keys from M to-device events` ([DehydratedDeviceManager.ts:259](../../../matrix-js-sdk-v2/src/rust-crypto/DehydratedDeviceManager.ts#L259)).
- [ ] Ramp 25% → 50% → 100% over 2 weeks if telemetry remains clean.
- [ ] Exit: 100% of active users on v2; no UTD-rate regression vs legacy baseline.

### Phase 5 — Server-side sweep (Strategy B)

- [ ] After 30 days at 100% on v2, run Synapse admin script to forward residual to-device events from legacy ghosts to new ghosts for users who never drained on legacy.
- [ ] Exit: residual orphan-ghost count drops to zero.

### Phase 6 — Cleanup

- [ ] Remove dead `getDehydrationKey` wiring from [MatrixClientPeg.ts:448-457](../../src/MatrixClientPeg.ts#L448-L457).
- [ ] Remove [SecurityManager.ts:162](../../src/SecurityManager.ts#L162) dead `getDehydrationKey()`.
- [ ] Remove orphan translations in [src/i18n/strings/nb_NO.json](../../src/i18n/strings/nb_NO.json) lines 2038–2043.
- [ ] Drop `getDehydrationKeyCallback` from `verji-cryptosetup-module` (already dropped in module v2; this just removes the consumer hook in `matrix-react-sdk-module-api` if reasonable).
- [ ] Retire `UIFeature.DehydratedDevices` flag (now unconditionally on).

## 8. Verification & observability

- **Unit / integration tests**: extend tests around `MatrixClientPeg.initClientCrypto` for the new dehydration call site, including the 4S-not-ready short-circuit (must not throw, must log warning, must not retry tightly).
- **End-to-end**: a Playwright (or manual) flow on staging — fresh SSO login, observe `PUT /dehydrated_device`; log out; log in fresh on a second device; observe `GET /dehydrated_device` followed by `POST /dehydrated_device/{id}/events`; confirm decryption of an offline-delivered message that was sent between the two logins.
- **Metrics**: per-user UTD-event counter with cohort tags (legacy vs v2); server-side count of pending events on legacy ghost devices over time (should trend to zero); count of new MSC3814 ghost devices created per day.
- **Rollback**: the `UIFeature.DehydratedDevices` flag stays in place for at least one quarter post-100% so individual deployments can be reverted via config change without redeploy.

## 9. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Synapse MSC3814 work slips → entire client plan blocks | Medium | High | W2/W3 work proceeds in parallel so client is ready when server lands; no client work is wasted |
| 4S not ready at the dehydration call site (race with SSO bootstrap) → silent disable | Medium | Medium | Place dehydration init *after* the bootstrap promise resolves, not in parallel; add a one-time retry on next sync if `isSecretStorageReady()` was false |
| Legacy `element-web/` drain patch never reaches infrequent users → message loss for those users | Medium | Medium | Strategy B sweep catches the residual; in addition, hold inactive users on legacy until drain flag set |
| Per-user staged rollout requires user-targeting infra Verji doesn't have | Medium | Medium | Coordinate with whoever owns Verji deploy/feature-flag plumbing; if not available, fall back to percentage-based rollout via config and accept slightly higher loss tail |
| `verji-cryptosetup-module` v2 incompatible with legacy element-web during transition | High (by design) | Low | Maintain both v1 and v2 of the module during the bridge; document which build consumes which |
| Pre-existing 4S key on Verji users was set up via an older flow that doesn't satisfy `isSecretStorageReady()` (e.g. missing `default_key` account-data entry) | Low–Medium | High | Audit a sample of production accounts for 4S completeness *before* cutover; if gap exists, add a one-shot bootstrap-completion step at v2 first-login |
| MSC3814 still unstable upstream → endpoint URLs or semantics change in a future matrix-js-sdk release | Low (short-term) | Medium | Pin matrix-js-sdk version during rollout; treat upstream MSC3814 changes as a separate evaluation gate |
| `setInterval` for periodic re-dehydration ([DehydratedDeviceManager.ts:288](../../../matrix-js-sdk-v2/src/rust-crypto/DehydratedDeviceManager.ts#L288)) doesn't survive page reloads, so a long-running tab is needed for the 7-day rotation to actually fire | High | Low | Acceptable — every login also triggers `start()` which creates a new ghost. The interval is a refresh-while-online mechanism, not the primary trigger |
| User who completed Strategy A drain on legacy then never logs into v2 ends up with no ghost at all (no MSC2697, no MSC3814) | Medium | Low | Acceptable for the duration of inactivity; v2 creates the ghost on first login |

## 10. Comparison with the Rollback PRD

| Dimension | Rollback (defer + backport) | Embrace (this PRD) |
|---|---|---|
| Up-front engineering effort | Low | Medium (W2 + W3 + W4 = ~3–6 engineer-weeks) |
| Ongoing engineering effort | Medium (weekly backports) | Low (post-rollout) |
| Crypto-correctness risk | None (existing code path) | Medium (new wiring at safety-critical layer) |
| Server-side dependency | Same (Synapse MSC3814) | Same (Synapse MSC3814) |
| Preserves absorption work | No — paused | Yes — migration completes |
| Time to caught-up with upstream | Long (resume + replay backports) | Short (already there) |
| Loss of recently-shipped Element features (TAC, pinned messages, etc.) | Yes | No |
| Reversibility if discovered to be wrong | High | Medium (UIFeature flag for a quarter, then full forward) |
| Bridge length tolerance | 6–12 months comfortable | Indifferent (only blocks on server) |

The two PRDs share the same critical-path dependency: **Synapse MSC3814 support in production**. The difference is what the client team does in the meantime and what shape the codebase has on the other side. The Rollback path is cheaper this quarter and more expensive every subsequent quarter; the Embrace path front-loads the cost and ends with the codebase upstream-aligned.

This PRD recommends reading both and deciding based on (a) confidence in the Synapse MSC3814 timeline, (b) tolerance for the engineering cost spike of the migration drain, and (c) the strategic value Verji places on staying close to upstream Element.

## 11. Contingencies

- **Synapse can't be persuaded to update `.well-known`**: relax the gate in [dehydration.ts:24-32](../../src/utils/device/dehydration.ts#L24-L32) — drop the `wellknown?.["org.matrix.msc3814"]` check and rely solely on `isDehydrationSupported()`. This is a Verji-private patch to a small upstream function; low risk; reversible. Document as a Verji customization with a `// VERJI` marker per [CLAUDE.md](../../../CLAUDE.md).
- **Strategy A drain patch is rejected by ops as "too much risk to legacy production"**: fall back to Strategy B alone, accept a longer drain window (e.g., 90 days), monitor UTD rates, and hand-recover the worst-affected users via support tickets.
- **W3 module bootstrap reveals 4S incompleteness on a meaningful slice of accounts**: extend the cryptosetup module to perform the missing 4S setup steps (e.g., `bootstrapSecretStorage`) on first v2 login, *before* `initialiseDehydration` is invoked.

## 12. Open questions

1. **Synapse MSC3814 roadmap and target version.** Same blocker as the Rollback PRD; the answer drives every phase exit date here. If unknown, this PRD is an aspirational document.
2. **Does Verji have user-targeting feature-flag infra at client load time?** Strategy A's per-user gate (Phase 4) depends on it. If not, design adapts (percentage-based rollout) but loss tail grows.
3. **What fraction of Verji users currently have a populated MSC2697 ghost device?** Drives the actual blast radius of the drain. Pull from server inventory before approval.
4. **How long is the typical interval between user logins?** Drives the Strategy A window length. Pulled from product analytics.
5. **Is there an SSO-flow regression test we can repurpose for the new wiring?** Want to avoid re-discovering 4S race conditions during rollout.
6. **What happens to the four `// VERJI MERGE` TODOs from the Dec 2024 absorption** ([CLAUDE.md](../../../CLAUDE.md))? At least one is dehydration-adjacent ([MatrixClientPeg.ts:348](../../src/MatrixClientPeg.ts#L348)) — this PRD resolves that one. The other three should be reviewed in the same workstream.
